## Phase Goal

**As a** solo builder presenting Pay-When-Done, **I want to** run the app on a public Render HTTPS URL with role-based accounts, private photo and video storage and written results for every risky vendor behaviour, **so that** the money and evidence code in later phases is built on verified ground.

**This plan's slice (AUTH-02 refusal):** a signed-in user can press "try another role's action" on the dashboard and see the server refuse it, while their own role's action succeeds.

<objective>
Add the server-side authorization helpers (role and job relationship), one route wrapper that every role-restricted handler uses, three role ping actions, a dashboard panel that exercises them, and live smoke tests for role refusal and session persistence. Purpose: AUTH-02 requires the server to check role and job relationship on every decision. Phase 2's transition table reuses `assertJobParty` and `withActor`, so the contract is fixed and tested now.

</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-07-01 | Elevation of privilege | A role route forgetting its check | high | mitigate | Every role route is `withActor([...], handler)`; acceptance counts the wrapper in all three routes; live smoke asserts 403/401 |
| T-01-07-02 | Elevation of privilege | Acting on another party's job (Phase 2 consumers) | high | mitigate | `assertJobParty` is data-driven and table-tested now, including id collisions across roles and unassigned jobs |
| T-01-07-03 | Spoofing | Client-side-only guards | medium | mitigate | `proxy.ts` only redirects; the server wrapper decides; the UI just shows the server's status |
| T-01-07-04 | Information disclosure | Error detail in 401/403 bodies | low | mitigate | Bodies are `{ error: "unauthenticated" | "forbidden" }` only |
</threat_model>
